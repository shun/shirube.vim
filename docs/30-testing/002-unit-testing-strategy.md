# ユニットテスト戦略と設計仕様 (Test Strategy & Design)

## 1. 目的と品質目標 (Objectives)
本プロジェクトでは、ファイルシステム操作という不可逆かつ危険な操作を扱います。したがって、**「データ消失の防止」** と **「意図しない変更の防止」** が品質保証（QA）の最重要項目です。

これらを保証するため、以下の観点でテストを設計・実施します。

## 2. QAテスト観点 (Test Perspectives) 🔍

単にコードパスを通すだけでなく、以下のQA観点に基づいてテストケースを選定します。

| 観点 | 説明 | 具体例 |
| :--- | :--- | :--- |
| **機能正確性 (Correctness)** | 仕様通りに正しく動作するか（正常系）。 | コピーしたファイル名に `_copy` が付くか。 |
| **堅牢性 (Robustness)** | 不正な入力や予期せぬ状態でクラッシュしないか（異常系・準正常系）。 | 空文字、存在しないID、不正なURLスキーム。 |
| **境界値分析 (Boundary)** | 処理の分岐点となる境界条件での挙動。 | パス末尾のスラッシュ有無、ルートディレクトリ、空のディレクトリ。 |
| **状態遷移 (State)** | 状態の変化が正しく反映されるか。 | リネーム後のパスが次の操作の起点として認識されるか。 |
| **回帰 (Regression)** | 修正したバグが再発しないことの保証。 | `basePath` にスラッシュが含まれる際の文字欠け問題。 |

## 3. テスト設計詳細 (Test Specification)

実装済みのユニットテストにおける具体的な確認項目と、その意図（Why）を記述します。

### 3.1 ユーティリティ (`util_test.ts`)
システムの基礎となるパス操作関数の信頼性を検証します。

| テスト対象 | ケース/条件 | 観点 | 期待値 (Expected) |
| :--- | :--- | :--- | :--- |
| `normalizeUrl` | 正常な shirube URL | 正確性 | そのまま返却されること。 |
| | 数値や空文字 | 堅牢性 | エラーをスローすること。 |
| `urlToPath` | `shirube://` | 正確性 | パス部分のみ抽出されること。 |
| | `file://` | 堅牢性 | サポート外としてエラーになること。 |
| `generateCopyName` | **ファイルコピー** | 正確性 | `_copy` サフィックスが付与されること。 |
| | **ディレクトリコピー** | 境界値 | 末尾の `/` を維持しつつ `_copy` が付与されること。 |
| | **重複あり** | 状態 | 既に `_copy` がある場合、`_2` にインクリメントされること。 |
| | **[BUGFIX] 親パス末尾 `/`** | **回帰** | **パス切り出し時にファイル名の先頭が削られないこと。** |

### 3.2 構文解析 (`parser_test.ts`)
ユーザーが編集したバッファ（テキスト）を、操作可能な構造データに変換する重要なプロセスです。

| テスト対象 | ケース/条件 | 観点 | 期待値 (Expected) |
| :--- | :--- | :--- | :--- |
| `parseBuffer` | 既存エントリ (`/ID name`) | 正確性 | IDと新しいパスが正しくマッピングされること。 |
| | 新規作成 (`name`) | 正確性 | IDなしとして `created` リストに追加されること。 |
| | リネーム | 状態 | IDはそのままで、名前（パス）だけが変更されていること。 |
| | **コピー (ID重複)** | 正確性 | 同じIDが複数行ある場合、`duplicated` として検出されること。 |
| | コピー (内容変更) | 境界値 | コピー行の名前を変更しても、元のID由来として追跡されること。 |
| | 未知のID | 堅牢性 | `BufferState` にないIDはエラーとして報告されること。 |
| | 不正フォーマット | 堅牢性 | フォーマット崩れ（IDなし、空の名前）を適切にエラー/無視として扱うこと。 |

### 3.3 差分検出 (`diff_test.ts`)
現在の状態とパース結果を比較し、副作用（Action）を決定するロジックです。**最もデータ消失リスクが高い部分**であるため、慎重に設計します。

| テスト対象 | ケース/条件 | 観点 | 期待値 (Expected) |
| :--- | :--- | :--- | :--- |
| `buildActions` | 変更なし | 正確性 | Action が空であること。 |
| | 移動 (Move) | 正確性 | `src` と `dest` が正しく設定された `move` Action が生成されること。 |
| | 作成 (Create) | 正確性 | `create` Action が生成されること。 |
| | 削除 (Delete) | 安全性 | バッファから消えたIDに対して `delete` Action が生成されること。 |
| | コピー (Copy) | 正確性 | 重複IDに対して `copy` Action が生成されること。 |
| | **複合操作** | 状態 | 移動、作成、削除が混在しても、全ての Action が生成されること。 |
| | **実行順序** | 安全性 | 依存関係を壊さない順序（作成→移動→削除など）でソートされていること。 |

## 4. 今後のテスト計画 (Future Scope)

現在のユニットテストではカバーしきれない、より広範囲なテスト観点です。

### 4.1 統合テスト (Integration Testing)
- **観点**: 実際の OS ファイルシステムとの不整合。
- **内容**: 実際にファイルを作成し、権限エラーやロック競合が発生した場合の挙動を確認する。

### 4.2 ビジュアル・リグレッションテスト
- **観点**: UI/UX の劣化。
- **内容**: `feedkeys` を用いた操作シミュレーションで、カーソル位置やハイライトが意図通りか確認する（`docs/30-testing/001-headless-checks.md` の自動化）。
